# 管理清單人工處理紀錄

待校正清單與錯誤回報各自顯示「待處理／處理中／已處理」。
點選「更新處理狀態／查看紀錄」，選擇狀態並填寫備註後儲存。
可將已處理項目重新設為待處理；每次操作另存一筆歷程。

## 與原始資料的界線

- 不修改 `ErrorReports.Status`、歌曲內容或校正工作，也不會自動套用歌詞。
- 開啟頁面、修復歌詞或部署程式都不會自動結案。
- 舊回報預設待處理，不從歷史修復紀錄推測完成。
- 每次儲存記錄伺服器認證的登入管理員、UTC 時間、狀態與必填備註。
- 原始回報內容或校正工作版本改變後，不沿用較早的完成記號；
  舊歷程仍保留。此判斷不是實播驗證，也不代表新工作已通過。
- 已處理項目仍留在原清單；待校正歌曲退出清單後，原處理紀錄網址
  仍可查閱。紀錄頁顯示最近 50 筆，資料庫保留全部歷程。

## 部署

先備份並執行 `docs/sql/007-management-work-events.sql`，
再部署主應用 DLL、Views DLL 與 `management-queues.css`。
DDL 僅建立獨立的 `dbo.ManagementWorkEvents` 與索引，不回填舊資料。
網站不會在讀取或儲存時自動建立資料表。
資料表缺失時回應 503，不能把「讀取失敗」當成待處理。
回滾程式時保留此附加資料表，不刪除既有稽核紀錄。

## 安全與衝突

僅資料庫 `Users.Manager` 認定的管理員可讀寫，POST 必須附防偽 token。
處理者不接受表單傳入；項目 ID 必須對應現存的歌曲或已核實唯一鍵的回報。
來源指紋及歷程版本在同一個 Serializable 交易內再次核對，
同項目以交易鎖序列化。舊分頁或其他人先儲存時回應 409，不覆蓋。
409 畫面保留本次未儲存備註，需核對最新內容後重新提交。
若回應 503 或連線中斷，先重新讀取歷程確認結果，勿盲目重送。

JSON 清單及既有音樂自動化 API 維持原始契約，不提供此人工標記寫入入口。
